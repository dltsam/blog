地图单独运行时，点击图层弹出信息窗很正常；嵌入父页面后，窗体却离目标越来越远。这种偏位常被当成一个 CSS 数值问题，实际需要先回答：**这个坐标是相对于谁的？**

在微前端或嵌入式页面中，至少可能同时存在地图视图坐标、子应用容器坐标、父页面视口坐标。父页面若对容器做了缩放或平移，`clientX`、容器内偏移和地图 SDK 的屏幕坐标就不能直接混用。

## 把转换链写出来

排查时，我会先记录四个量：点击点在浏览器视口中的位置、子应用容器的 `getBoundingClientRect()`、实际缩放比例、弹窗被挂载的 DOM 容器。随后画出从事件坐标到弹窗定位坐标的转换链。

若弹窗挂在父页面，就把子应用内坐标转换到父页面视口；若挂在子应用内部，就只使用该容器自己的坐标。不要给坐标反复乘缩放值，也不要用一个在固定窗口尺寸下“刚好对齐”的常量补偿。

```text
视口坐标 → 减去容器原点 → 按实际缩放还原 → 子应用内坐标
```

这只是转换关系的示意。真实实现还要看容器是否滚动、是否有嵌套变换，以及地图 SDK 返回的究竟是哪一种坐标。

## 尺寸变化要重新测量

父页面侧栏开合、窗口缩放、浏览器缩放比例变化，都可能改变容器边界。依赖初始化时量到的一次尺寸，弹窗迟早会再次偏位。对嵌入容器使用 `ResizeObserver`，在尺寸变化时更新地图视图尺寸与定位基准，比维护一组屏幕宽度特例更可靠。

还要区分两件事：地图上的锚点在哪里，弹窗自身有多宽、多高。先让锚点落在正确位置，再处理弹窗越界、遮挡和层级；把这两类问题混在一个偏移量里，会让后续修改难以判断。

## 在真正的父页面里验收

子应用独立运行通过，只能说明独立运行通过。嵌入场景要在实际父页面测试：不同窗口宽度、侧栏状态、地图缩放级别、靠近屏幕边缘的点击，以及地图与弹窗之间的鼠标交互。必要时记录容器矩形和最终弹窗矩形，对照目标点的位置。

构建成功也只是代码可打包。坐标问题的证据应来自真实布局中的位置和交互。
